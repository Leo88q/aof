# Правовые документы, приватность и выпуск

Версия инструкции: 2026-09-28. Это техническая процедура, не юридическое заключение.

## Текущий статус юридических маршрутов

Проекты условий, политики и архив сняты из рабочего дерева; прежние URL `/legal/*` и
`/legal/archive/*` показывают только локализованное уведомление о том, что документы **не
опубликованы**. `/legal/cookies` дополнительно показывает фактическую таблицу хранения в браузере.
Настройки согласия и предупреждение перед подключением кошелька остаются доступными; они не
заменяют утверждённые условия. Удаление исходников не очищает Git-историю, ранее опубликованные
сборки и кэши. Режим инкогнито не скрывает публичные транзакции Solana или сетевые данные.

## До production: заполнить владельцу / юристу

Для запроса к юристу одной пересылкой есть бриф `docs/LAWYER_BRIEF_2026-09-28.md` (факты проекта + 23 вопроса).

`frontend/src/legal/operator.json` — **публичные** реквизиты, не секрет-хранилище. Пофайловый
чек-лист «что прислать владельцу и где это станет видно» — `docs/OPERATOR_DATA_CHECKLIST.md`,
машинный список недостающего — `npm run legal:report` (тот же валидатор, что держит релиз):

1. Юрлицо/ФИО оператора, страна, почтовый адрес, регистрационные сведения либо правомерное обоснование неприменимости.
2. Рабочие email поддержки/претензий, privacy/DSAR и security. Проверить получение тестовых писем, ответственного и резервного исполнителя. Не ставить вымышленные адреса.
3. Официальный HTTPS origin без завершающего `/`, применимое право/порядок споров, страны аудитории. Страна разработчика не определяет автоматически применимые законы.
4. Фактические процессоры (юридическое имя, цель, страна), DPA, механизмы международной передачи; DPO/представитель или обоснование неприменимости.
5. Конкретные сроки хранения для каждой цели, schedule удаления/анонимизации, резервные копии, исключения для законных требований.
6. До любого выпуска оператор и юрист создают и проверяют новые документы с учётом фактов проекта: возраст/юрисдикции, токены/NFT, платная случайность, MiCA/KYC/AML/санкции, маркетинг, потребительские права, возвраты, интеллектуальные права. Нельзя утверждать `approved: true`, пока отсутствуют проверенные и опубликованные тексты.
7. Для будущих публикаций согласовать версию и дату с юристом. При изменении правил необязательной обработки повысить `CONSENT_VERSION` и обновить тесты; не возвращать снятый архив автоматически.
8. Только после проверки текстов и фактов установить `approved: true`. Флаг — декларация оператора, не автоматическая юридическая экспертиза.

## Сборка и релиз

```bash
cd frontend
npm ci
npm run test:privacy
npm run test:security
npm run build:release
```

`build:release` теперь собирает фронтенд, проверяет локализацию и отсутствие исходников/секретных файлов в публичном выводе, **но не останавливается на юридических полях**. `npm run release:check` и `npm run legal:report` показывают пробелы справочно. Сборка не публикует ничего сама и не означает юридическое разрешение на запуск.

Пока контакт и официальный HTTPS origin не проверены, `security.txt` не генерируется, а dev-sitemap с `localhost` исключается из release-вывода. После проверки реквизитов отдельная команда `node scripts/legal-release.mjs --emit-security` может выпустить security.txt и исправить карту сайта; это не заменяет реальную проверку доступности контакта и документов. Хостинг с root `frontend` и output `dist` может использовать `npm run build:release`; ограничить staging и отдельно принять решение о публичном запуске.

После деплоя проверить реальные HTTP headers, доставку security.txt (не SPA index.html), корректность origin, expiry и работоспособность контактов. Обновлять security.txt до истечения срока и при смене контакта. HTTPS origin validator — синтаксическая проверка, не подтверждение владения доменом или доставки email.

## Consent: гарантии и ограничения реализации

`src/legal/consent.ts` разрешает функциональные записи только при действующем выборе нужной версии. Отказ и GPC запрещают их; при отзыве удаляются четыре известные приложению записи, а не всё localStorage произвольно. При истечении срока очистка выполняется при следующем посещении/возврате в окно. Браузер, закрытый пользователем, не может выполнять удаление.

`nf:privacy-choice:v1`: случайный ID записи, версия, время, expiry и категории. Это **локальная квитанция**, без IP/кошелька, не централизованный доказательный журнал договора. При недоступном storage приложение остаётся рабочим; выбор временный. Аналитика/маркетинг не подключены и разрешений на них нет. Любой будущий SDK должен проходить отдельную проверку и загружаться только после своего согласия.

Не считать таблицу приложения полным cookie scan production: CDN/WAF, wallet extensions, mobile browsers и будущие SDK проверяются отдельно. `walletName` относится к сторонней wallet-adapter библиотеке; автоподключение отключено, но lifecycle её storage надо проверить с реальными кошельками. Не хранить JWT/секреты в этих записях.

## Начальная карта данных — требует подтверждения runtime

| Данные | Доказательство в коде | Цель / предлагаемое основание | Хранение / получатели / следующий шаг |
|---|---|---|---|
| Адрес кошелька, подпись операции | `src/lib/wallet.ts`, backend `security/walletProof.ts` | Запрошенная операция / договор; anti-replay / безопасность | Утвердить сроки proof/nonce, API/RPC processor, доступы |
| Профиль, прогресс, квесты, инвентарь | `aof_backend/prisma/schema.prisma`: Profile, QuestProgressDb, FarmPlot и др. | Игровой сервис / договор | Основная БД; нужны TTL, экспорт, удаление и проверка связей |
| IP, User-Agent, адрес, детали | schema: AuditRecord, AuditLog | Безопасность / оценённый законный интерес либо применимая обязанность | Нужны минимизация details, retention, права операторов, проверка Pino/redaction |
| Fingerprint устройства | schema: DeviceFingerprint, SybilFlag | Антифрод; оценить необходимость и применимость ePrivacy/GDPR | Наличие таблицы не доказывает разрешённость сбора; проверить активные клиенты, DPIA и сроки |
| Push-токен устройства | schema: DeviceToken, NotificationQueue | Уведомления, запрошенные пользователем; отдельная оценка согласия | Проверить permission flow, провайдера и удаление при отписке |
| On-chain операции / контрагенты / fraud evidence | schema: ChainTx, ChainEvent, FraudCase | Исполнение операций, расследование | Публичная сеть + индексатор; нельзя обещать удаление блокчейна; fraud hold требует оспаривания |
| Локальный журнал, вводный экран, звук/анимация | `consent.ts`, `ExtraSections.tsx`, `FarmDashboard.tsx`, `manorFx.ts` | Функциональное хранение / предварительный opt-in | На устройстве; отказ/GPC/отзыв; квитанция 180 дней |
| Web access logs и резервные копии | Фактический хостинг не предоставлен | Уточнить по каждой цели | Нужны хостинг/CDN страны, DPA, retention и восстановление |

Основания в таблице — предложения для проверки, не установленная законность. Wallet/IP/fingerprint считать потенциально персональными данными. Шифрование, SCC и «анонимность» не обещать без доказательств.

## DSAR: рабочая процедура для назначенного оператора

1. Зарегистрировать запрос в закрытой системе обращений: дата получения, тип права, применимая юрисдикция, контрольный срок, ответственный. Не публиковать запрос в GitHub.
2. Проверить личность соразмерно риску. Для кошелька — отдельное одноразовое domain-bound expiring сообщение с назначением DSAR, проверяемое сервером; не seed, не перевод, не повторное использование transaction proof.
3. Определить данные по полной карте, включая таблицы, логи, процессоров, fraud cases, экспорт и backups; исключить данные третьих лиц из ответа.
4. Реализовать и проверить экспорт/исправление/удаление с авторизацией, транзакционностью, защитой от IDOR и журналом действий. Эти серверные DSAR-endpoints **пока не добавлены**; никакая кнопка UI не имитирует их выполнение.
5. Сообщить обоснованные исключения, сроки backup expiration и невозможность удалить on-chain историю. Применять suppression/tombstone при восстановлении, чтобы удалённые данные не возвращались в рабочую обработку.
6. Ответить в законный срок (обычно 1 месяц по GDPR); допустимое продление и причины сообщить своевременно. Дать путь обжалования/обращения к компетентному органу.
7. Фиксировать исполнение без избыточного копирования персональных данных. Автоматические retention jobs требуют тестов и согласованной политики — не удалять экономические/audit ledgers вслепую.

## Тесты и ручная приёмка

- `npm run test:privacy`: consent schema/expiry/version/GPC, storage gating/revoke, no external fonts, production CSP, release validation/security.txt.
- `node --test tests/readiness/*.test.cjs` из корня; `npm run test:security` из frontend.
- Дополнительный browser smoke: установить Playwright в отдельное tooling-окружение, затем `PLAYWRIGHT_MODULE_PATH=/absolute/path/to/playwright/index.mjs node frontend/tests/privacy-browser.mjs`. Для стандартной установки доступного `playwright` env не нужен; установить Chromium командой Playwright. Можно указать `PLAYWRIGHT_EXECUTABLE_PATH`, `PRIVACY_TEST_URL`. Ранее проводилась локальная проверка со старыми проектами; обновлённый smoke для снятых документов
в этом окружении не запускался (Playwright недоступен). Production не тестировался.
- Browser smoke проверяет уведомления на бывших документных маршрутах, статус архивного URL, отсутствие горизонтального переполнения, отказ/разрешение/отзыв, GPC, отсутствие Google Fonts и JS page errors на этих маршрутах. Это не кошельковый e2e, не WCAG-аудит и не проверка реального API.
- Ручная приёмка: клавиатура/скринридер, 200% zoom, мобильные кошельки, browser storage disabled, другие вкладки, срок согласия, production headers/CSP violation reports, все внешние SDK и network requests, контакты и наличие проверенных документов перед публикацией.
