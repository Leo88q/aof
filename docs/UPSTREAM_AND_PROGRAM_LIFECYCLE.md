## 1. Реестр программ — единственный источник правды

`security/program-registry.json` — все наши программы, внешние CPI-цели и выведенные компоненты. Проверяется на каждом коммите (`node scripts/security/program-registry.mjs --check`):

- каждый `declare_id!` и каждый адрес в `Anchor.toml` (localnet/devnet/mainnet), IDL и `watchtower/addresses.json` совпадает с реестром;
- `frontend/src/lib/txGuard.ts` содержит **все** адреса программ: клиент не пустит легитимную программу и не пропустит чужую;
- адреса, зашитые в Rust (`vrf.rs`), включая queue/state PDA оракула и Address Lookup Table, привязаны к записям `external[]`;
- у активной программы есть план по upgrade authority и хотя бы один монитор;
- у депрекейтнутой/выведенной — `evidence`, `successor`, `authority` и `drained: true`;
- каждая апстрим-зависимость имеет пин, который реально находится в lock-файле, и advisory-источник.

Добавление программы/CPI-цели — отдельный ревьюируемый диф, как новый MCP-сервер в политике агентов.

## 2. Жизненный цикл

| Этап | Требования |
|---|---|
| Новый деплой (beta, тест) | запись в реестре с `status: test-only`, отдельный адрес, отдельные authority; в реестре видно, что это не прод |
| Прод | запись `active`, план по upgrade authority, мониторы: authority-change, upgrade, balance (если хранит ценность), security-advisories |
| Депрекейт | сначала **вывести ценность** (`drained: true`), затем снять/сжечь authority (upgrade authority → None или Squads с отказом от обновлений), вывести ликвидность, закрыть LP/NFT-аккаунты; в записи — evidence и successor |
| Спящий, но нужный | не считается безопасным: мониторится наравне с активным, потому что «неактивный» компонент — цель (Raydium V3, Aztec) |
| Форк/копия общего кода | отдельная запись + ссылка на апстрим и порядок переноса security-фиксов (случайность живёт только в `aof-core/src/vrf.rs`; `scripts/sync-quests-vrf.py --check` запрещает вторую копию) |

Правило «депрекейт без drain — это находка» встроено в проверку: `deprecated` без `drained: true` роняет сборку.

## 3. Апстрим-дозор (#116, #128)

1. **Пины видны и проверяемы**: `security/upstream-dependencies.json` (репозиторий, критичность, где пин, advisory-источники, что мониторим). Offline-проверка — на каждом коммите, online — еженедельно (`.github/workflows/upstream-watch.yml`): OSV по установленным версиям + последние релизы GitHub. При находке workflow открывает issue, а не обновляет зависимости сам.
2. **Свой фикс: сначала приватно.** Ветка/PR без публикации → сборка → деплой (или подтверждённая готовность деплоя) → и только потом публикация коммита и advisory. Публичный diff до деплоя — готовая инструкция для атакующего, в том числе для ИИ-агента.
3. **Отставание от апстрима — риск**: смотрим не только «есть ли новая версия», но и **security-коммиты в ветках** (Liquid-урок: фикс был в ветке, но не в теге). Для критичных компонентов (оракул, SPL Token, Anchor) фиксируем дату последнего обновления и алертим при отставании больше квартала.
4. **Разбор находки**: обновить пин вместе с lock-файлом, проверить форки/копии, прогнать CI, обновить `updatedAt` реестра. Автоматический merge ботов не включаем.

## 4. Изменения конфигурации цены и комиссий (#117)

Ошибку конфигурации боты эксплуатируют в одной транзакции, поэтому «посмотрим после выката» не работает:

1. Изменение параметров цены/комиссий/лимитов сначала прогоняется **на форке состояния основной сети** (`solana-test-validator --account ...`), с fuzz на границах и проверкой инвариантов.
2. Выкат — с ограничениями: кап на объём операций, стартовая пауза, постепенное снятие; аварийный откат подготовлен заранее (`set_*` + `set_paused`).
3. После выката — автоматическая сверка: пул/ордербук отдают цену в ожидаемом диапазоне; расхождение → пауза и алерт.
4. Никаких изменений цены в одной транзакции с пользовательскими действиями и без таймлока на исполнение там, где это возможно.

## 5. После инцидента: «зачистка класса» (#129)

Aztec потерял два моста за неделю, Transit Finance — повторно спустя годы. После любого инцидента (у нас или у похожего проекта):

1. Искать тот же класс бага во **всех** программах, старых версиях, форках и тестовых деплоях; каждую находку — в реестр, каждую неиспользуемую — осушить.
2. Не считать «неактивный» компонент безопасным; для внешне неактивных — мониторинг балансов и authority.
3. Проверить, что исправление попало в **релиз/деплой**, а не только в ветку, и что все интеграторы/реплики обновились (Rain-урок).
4. Обновить `security/program-registry.json` (retired/deprecated + evidence) в том же PR, что и фикс.

## 6. Команды

```bash
# реестр: адреса, жизненный цикл, апстримы, ключи
node scripts/security/program-registry.mjs --check
node scripts/security/program-registry.mjs --json

# апстрим-дозор
node scripts/security/upstream-watch.mjs --check          # offline, каждый коммит
node scripts/security/upstream-watch.mjs --online         # OSV + GitHub releases
gh workflow run upstream-watch.yml                        # вручную, вне расписания
```
