# Бенчмарк release-профилей SBF

Статус: 2026-10-01. **Профиль в корневом `Cargo.toml` не менялся: измерений нет.** В песочнице агента нет Anchor, Agave и
Rust, поэтому здесь готов только измерительный харнесс и его проверка на подменённом тулчейне. Сами сборки и замеры
выполняются на машине владельца.

Сейчас `[profile.release]` содержит только `overflow-checks = true` (его требует `CLAUDE.md`, проверяет readiness #115) —
остальное по умолчанию. Размеры `.so` из условия задачи (≈ 2.38 / 0.42 / 0.59 / 0.28 / 0.33 / 0.28 MiB) в песочнице не измерены.

## Чего нельзя предполагать (и харнесс не предполагает)

* что fat LTO поддерживается SBF-тулчейном — ячейка, которая не собралась, записывается как «профиль не поддержан» и исключается;
* что `"z"` меньше `"s"` — обе измеряются отдельно, победитель выбирается по байтам;
* что экономия составит 15–20% — процент вычисляется из измерений, а выигрыш меньше 2% оставляет baseline;
* что переопределение профиля вообще подействовало — если профили разные, а все наборы `.so` побайтно одинаковы, прогон
  объявляется недействительным (`overridesIgnored`), выбор не делается;
* что явная `opt-level = 3` совпадает с «текущим» — это две разные ячейки (`baseline` и `o3`); совпадение их хешей —
  проверка, а не допущение.

## Запуск (машина владельца)

```bash
node scripts/bench-sbf-profiles.mjs plan                       # что будет собрано (ничего не запускается)
node scripts/bench-sbf-profiles.mjs run                        # 10 сборок «coarse»
node scripts/bench-sbf-profiles.mjs run --matrix full          # 4 opt-level × 3 LTO × 2 codegen-units × 2 strip = 48 сборок
node scripts/bench-sbf-profiles.mjs run --with-cu              # + `anchor test --skip-build` и CU из target/cu-report.md на каждой ячейке
node scripts/bench-sbf-profiles.mjs run --rpc <devnet-url>     # + rent по живому RPC (только чтение, через devnet-deploy-estimator.py)
node scripts/bench-sbf-profiles.mjs report <results.json>      # пересчитать отчёт и выбор из сохранённых данных
```

Результаты — в `target/sbf-profile-bench/<время>/` (`results.json`, `report.md`, копии `.so` каждой ячейки, исходные
`.so` в `original/`). Профиль переопределяется через `CARGO_PROFILE_RELEASE_OPT_LEVEL / _LTO / _CODEGEN_UNITS / _STRIP`, а
`CARGO_PROFILE_RELEASE_OVERFLOW_CHECKS=true` ставится в каждой ячейке принудительно; ячейку с выключенным overflow-checks
харнесс не соберёт. Ни один файл репозитория не меняется.

## Что измеряется

| Метрика | Источник |
|---|---|
| размер каждого `.so` и сумма | `stat` после `anchor build --no-idl` |
| SHA-256 | файл `.so` |
| время сборки | wall-clock `anchor build` |
| CU по инструкциям (max / median), порог 150 000 (VRF-раскрытия — 175 000) | `target/cu-report.md` (**только aof_core**, только успешные транзакции) |
| rent по живому RPC | `getMinimumBalanceForRentExemption` через оценщик, политика `exact` |

Для остальных пяти программ замера CU нет: `tests/aof_cu_report.ts` читает только транзакции aof_core. Если нужен порог
150 000 CU и для них — отчёт придётся расширить отдельно.

## Как выбирается профиль

Чистая функция `choose` (покрыта тестами на синтетических данных): допустимы только ячейки, где собрались все шесть
программ, прошли тесты (если запускались), ни одна инструкция не выше своего порога (150 000 CU; VRF-раскрытия
`VrfPoolAdd`/`*Commit`/`*Reveal` — 175 000 CU, они ходят в Metaplex CPI после PR #35) и ни одна не выросла по CU больше
чем на 10% относительно baseline. Из допустимых берётся наименьший суммарный размер; при равенстве — меньший CU, затем
более простой профиль, затем имя. Выигрыш меньше 2% — профиль не меняем.

Отчёт печатает блок `[profile.release]` для победителя; применять его нужно **вручную после review**, оставив
`overflow-checks = true` первой строкой. После этого: пересобрать, `anchor test`, `cargo test --workspace --lib`, сверить
`target/cu-report.md` и пересчитать стоимость (`scripts/devnet-deploy-estimator.py compare`).

## Безопасность запуска

* keypair'ы программ **не читаются**; проверяется только наличие `target/deploy/<имя>-keypair.json`. Без них харнесс
  отказывает: `anchor build` при отсутствии ключа создаёт новый и тихо меняет идентичность программы;
* исходные `target/deploy/*.so` снимаются в `original/` и возвращаются побайтно в конце — в том числе при ошибке и по Ctrl-C;
* сеть — только при `--rpc` и только чтение.

## Что проверено, а что нет

Проверено в песочнице (подменённый runner): состав и env ячеек, принудительный overflow-checks, оркестрация, SHA-256 и размеры
против независимого подсчёта, возврат исходных `.so`, неприкосновенность ключей, отказ без keypair'ов до первой сборки,
детектор «профиль проигнорирован», правила выбора (порог CU, рост CU, минимальный выигрыш, равенство размеров), контракт
с оценщиком через локальный JSON-RPC. **Не проверено:** сама сборка (`cargo build-sbf`), реальные размеры, реальные CU, то, какие
из профилей (особенно LTO) поддерживает тулчейн Agave 4.2.1 / platform-tools v1.56.
