# Утечка: первые 15 минут
Версия 1 — 2026-09-28. Владелец инцидента и резервный контакт должны быть назначены **до релиза**. Этот документ не доказывает, что роли и доступы настроены.

## 0–3 минуты: локализовать
- Назначить ответственного, открыть закрытый журнал с UTC-временем. Не вставлять секреты в issue, чат, Actions logs или отчёт.
- Через заранее проверенный guardian/multisig включить предусмотренную программой паузу выплат/клеймов; остановить скомпрометированные подписывающие workers. Не отправлять неподготовленные транзакции в аварии.
- Ограничить доступ к затронутому сервису на хостинге. Сохранить минимальные доказательства в закрытое хранилище, запретить дальнейшие публикации логов.

## 3–10 минут: отозвать доступ
- API/бот/БД/SMTP/CI: создать отдельный минимально привилегированный credential в нужном окружении, обновить secret manager и сервисы, **отозвать старый**, проверить невозможность его использования. Если идёт злоупотребление — сначала немедленный отзыв и временный простой.
- Кошелёк: с чистого устройства подготовить новый hardware/multisig wallet. Авторизованные владельцы переводят доступные средства и меняют upgrade/admin/mint/freeze authorities по проверенному runbook. Замена файла ключа без on-chain смены authority ничего не исправляет.
- Инвалидировать затронутые сессии и refresh tokens, проверить доступы CI/хостинга. Ни seed, ни приватный ключ не передаются агенту.

## 10–15 минут: проверить и сообщить
- Проверить новые доступы, on-chain authorities, баланс, лимиты и журналы. Старые credentials не работают. При невозможности завершить — сервис остаётся остановленным, эскалация владельцу.
- Только **после ротации**, с отдельным согласованием владельца: план очистки истории `git filter-repo`/BFG, refs/PR/caches/artifacts и всех клонов. Переписывание истории не отзывает утёкшие ключи и не уничтожает внешние копии.
- Зафиксировать объём раскрытия персональных данных; юридическая оценка обязанности уведомить регулятора в течение 72 часов после обнаружения (где применимо) и пользователей при высоком риске.
- Возврат в эксплуатацию — после независимой проверки, с журналом решений. Postmortem и повторный аудит.

## Предотвращение
- Разделить dev/staging/prod, RPC/CI/бот/DB/operator/guardian; запретить переиспользование секретов. Ротация по политике провайдера и немедленно при подозрении.
- Установить pre-commit и выполнить `pre-commit install` в каждом клоне; проверить hook пробным синтетическим секретом вне Git. Наличие `.pre-commit-config.yaml` само по себе hook не активирует.
- Выполнять gitleaks и trufflehog на рабочем дереве, всех refs и **фактически публикуемом** output. Отчёты хранить закрыто, значения редактировать. Не включать сетевую проверку найденных credentials без разрешения владельца.
- Публиковать только `frontend/dist`; CI запускает `python3 scripts/security/check-public-output.py frontend/dist`. Для ручного деплоя выполнить этот gate самостоятельно, затем полный secret scan. Не грузить корень репозитория.
