# Стоимость и ёмкость деплоя на devnet

Статус: 2026-10-01. Документ описывает, **как считается** стоимость первого деплоя шести
программ AOF, **что именно проверено по исходникам**, а что можно подтвердить только на машине
владельца (в песочнице агента нет `solana`, `anchor`, `cargo` и нет доступа к RPC).

Инструмент: [`scripts/devnet-deploy-estimator.py`](../scripts/devnet-deploy-estimator.py),
тесты: `python3 scripts/test-devnet-deploy-estimator.py` и `python3 scripts/test-deploy-devnet.py`.

## 0. Коротко

1. **Неявного 2× у CLI нет.** В Agave `v4.2.1` (версия, на которую закреплён проект) `solana program deploy`
   без `--max-len` берёт ровно длину программы: `cli/src/program.rs:1414–1423`
   (`let program_data_max_len = if let Some(len) = max_len { … len } else { program_len }`),
   справка: «`[default: the length of the original deployed program]`». То же в `v3.0.0`, `v2.1.0`, `v1.18.26`.
   Прежняя оценка «45.557 SOL при max_len = 2×» предполагала 2× — это было допущением, а не поведением CLI.
   Реально прежний `deploy-devnet.sh` (без `--max-len`) залочил бы **1.00×**.
2. Поэтому проблема не «CLI удваивает», а **«решение о запасе принималось молча»**: без запаса первая же
   разросшаяся программа упирается в ёмкость. Теперь `max_len` — явная политика владельца, скрипт без неё отказывает
   и сам передаёт `--max-len` в каждый деплой.
3. **Ставка за байт — движущаяся цель.** Rent сейчас снижается ступенями (SIMD-0437: 6 960 → 6 333 → 5 080 →
   2 575 → 1 322 → 696 lamports/байт; шаги 3–5 ожидаются в Agave 4.4, ноябрь 2026). Любая зашитая константа
   устарела бы, поэтому оценщик берёт rent **только** из `getMinimumBalanceForRentExemption`.
4. Цифра 45.557 SOL согласуется (арифметически, не измерением) с размерами из задачи × 2 × **≈5 080** lamports/байт
   (ставка шага 2), а не с 6 960: при 6 960 вышло бы ≈62.5 SOL. То есть прежний расчёт, вероятно, уже брал
   ставку из RPC, но ошибся в предположении про 2×.
5. Баланс проверяется **до первой транзакции и по всем недостающим программам сразу**. `MIN_SOL=1`
   достаточностью не считается (раньше он только печатался и отсекал нулевой баланс).

## 2. Модель стоимости

Для каждой программы `i` с размером `.so` = `S_i` и `max_len` = `M_i`:

```
rent_pd_i   = getMinimumBalanceForRentExemption(45 + M_i)       # ProgramData, постоянно
rent_prog   = getMinimumBalanceForRentExemption(36)             # Program,     постоянно
buffer_i    = rent_pd_i                                         # временно: возвращается плательщику в deploy-tx
writes_i    = ceil(S_i / 1012)
fees_i      = fee(2 подписи) + writes_i * fee(1 подпись) + fee(2 подписи)   # create_buffer + Write×N + deploy
постоянно_i = rent_pd_i + rent_prog
```

Rent и комиссии приходят только из RPC; в расчёт **не** добавляется ещё одна «128-байтная надбавка»
(`getMinimumBalanceForRentExemption` уже учитывает её).

Последовательный деплой шести программ моделируется **событиями** (по порядку, как в загрузчике):
комиссия create_buffer → создание Buffer (+`rent_pd`) → комиссии Write → комиссия deploy → создание Program
(+`rent_prog`) → **возврат Buffer плательщику** (−`rent_pd`) → создание ProgramData (+`rent_pd`).
Накопленный отток плательщика — это и есть потребность; её максимум — «пик».

```
пик                = max по накопленному оттоку всех программ подряд
переходный_пик     = пик − (Σ постоянно + Σ комиссии)          # для модели выше = 0
минимальный старт  = пик + резерв комиссий + резерв оператора
```

Чего эта модель **не** делает (и тесты это пинят):

* не берёт «самую большую программу» — рента прошлых программ остаётся заблокированной, пока идут следующие;
* не складывает все буферы поверх постоянной ренты — буфер возвращается в той же транзакции, где платится ProgramData,
  поэтому «переходный пик» равен нулю; он станет положительным, только если порядок событий изменится (тест
  `test_transient_peak_appears_only_if_the_buffer_were_returned_late`);
* не прячет резервы: **резерв комиссий** (`DEPLOY_FEE_RESERVE_SOL`, по умолчанию 0.1) и **резерв оператора**
  (`OPERATOR_RESERVE_SOL`, по умолчанию = `MIN_SOL`, то есть 1) — отдельные строки таблицы. Резерв оператора обязан
  быть не меньше rent-exempt минимума системного аккаунта (по RPC), иначе ключ окажется ниже порога.

## 3. Политики `max_len`

| Политика | `max_len` | Переменные |
|---|---|---|
| `exact` | `S` (1.00×) | `PROGRAM_MAX_LEN_POLICY=exact` |
| `headroom` | `S + ceil(S·p/100)`, `p` = 1…99 (например 10, 15, 25) | `PROGRAM_MAX_LEN_POLICY=headroom PROGRAM_MAX_LEN_HEADROOM_PERCENT=15` |
| `legacy-2x` | `2·S` (2.00×) | `PROGRAM_MAX_LEN_POLICY=legacy-2x` — только как явное решение |

Правила (fail-closed, всё покрыто тестами): значение не задано или неизвестно — отказ **до любого обращения к сети**;
`headroom` без процента или вне 1…99 — отказ; процент вместе с `exact`/`legacy-2x` — отказ как противоречие;
`max_len < S` — отказ; `45 + max_len > 10 MiB` — отказ. Политика — решение **devnet-скрипта**: к mainnet не
применяется (скрипт и так отказывает при цели не `devnet` и при genesis-хеше, отличном от devnet).

### Иллюстративные цифры

> **Это не котировка.** Размеры взяты из текста задачи (≈ по MiB: core 2.38, market 0.42, quests 0.59, rebirth 0.28,
> liquidity 0.33, session_keys 0.28; сумма 4 487 905 Б), `.so` не собирались. Ставки — публичное расписание SIMD-0437,
> а не чтение RPC. Они показывают **чувствительность**; реальная таблица получается командой из §4.
> Формат ячейки: «заблокировано / **минимальный стартовый баланс**» (с резервами 0.1 + 1 SOL), SOL.

| lamports/байт | exact 1.00× | 1.10× | 1.15× | 1.25× | legacy-2x 2.00× |
|---|---:|---:|---:|---:|---:|
| 6 960 (до SIMD-0437) | 31.25 / **32.37** | 34.37 / **35.50** | 35.94 / **37.06** | 39.06 / **40.18** | 62.49 / **63.61** |
| 6 333 (шаг 1, mainnet 3.09.2026) | 28.43 / **29.56** | 31.28 / **32.40** | 32.70 / **33.82** | 35.54 / **36.66** | 56.86 / **57.98** |
| 5 080 (шаг 2, testnet 3.09.2026) | 22.81 / **23.93** | 25.09 / **26.21** | 26.23 / **27.35** | 28.51 / **29.63** | 45.61 / **46.73** |
| 2 575 (шаг 3, Agave 4.4) | 11.56 / **12.68** | 12.72 / **13.84** | 13.30 / **14.42** | 14.45 / **15.57** | 23.12 / **24.24** |
| 1 322 (шаг 4) | 5.94 / **7.06** | 6.53 / **7.65** | 6.83 / **7.95** | 7.42 / **8.54** | 11.87 / **12.99** |
| 696 (шаг 5, цель) | 3.12 / **4.25** | 3.44 / **4.56** | 3.59 / **4.72** | 3.91 / **5.03** | 6.25 / **7.37** |

Комиссии сети при этих размерах — порядка 0.022 SOL (≈4 440 Write-транзакций × 5 000 lamports + create/deploy), то
есть шум на фоне ренты. Для devnet «деньги» — это не SOL, а доступность faucet: чем меньше запас `max_len` и чем
ниже ставка, тем меньше SOL нужно выпрашивать.

Почему это важно для решения: **рента возвращаема при закрытии аккаунта, но закрытие программы необратимо для
адреса** (CLI: «Program … has been closed, use a new Program Id»), а менять Program ID нельзя. Значит, лишний запас
`max_len` — это замороженные сейчас SOL по сегодняшней (высокой) ставке, а не «страховка, которую можно вернуть».

## 4. Как пользоваться

```bash
# 1. Таблица для всех политик на ЖИВОМ devnet-RPC (read-only, ничего не отправляет)
python3 scripts/devnet-deploy-estimator.py compare --from-registry --artifacts target/deploy

# 2. Детальный расчёт выбранной политики и проверка баланса оператора
PROGRAM_MAX_LEN_POLICY=headroom PROGRAM_MAX_LEN_HEADROOM_PERCENT=15 \
python3 scripts/devnet-deploy-estimator.py plan --from-registry --artifacts target/deploy \
        --payer "$(solana address -k solana/keys/aof-authority-devnet.json)"

# 3. Сам деплой (сухой прогон по умолчанию; --apply — только по вашему решению)
PROGRAM_MAX_LEN_POLICY=exact AOF_DEPLOY_TARGET=devnet scripts/deploy-devnet.sh
```

`--json` печатает машиночитаемый результат вместе с журналом RPC-вызовов (метод, параметры, ответ) — это и есть
доказательство, что rent получен из сети, а не из кода. В отчётах печатается только хост RPC (в пути/query бывает ключ).

Коды выхода оценщика: `0` готово · `2` неверный ввод или политика · `4` не хватает баланса ·
`5` RPC недоступен или ответил неправильно · `6` не тот кластер (genesis ≠ devnet) · `7` проверка после деплоя не сошлась.

`deploy-devnet.sh` теперь идёт в семь шагов; шаг 5 («Ёмкость программ и баланс до первой транзакции») печатает таблицу и
завершается отказом при дефиците **до первого `solana program deploy`** — и в сухом прогоне тоже.
После каждого деплоя скрипт проверяет в сети: аккаунт исполняемый, владелец — upgradeable-загрузчик, authority
ожидаемая, ёмкость = `max_len`, sha256 байткода равен локальному `.so`.

## 5. Если программа вырастет: upgrade и `solana program extend`

Из `v4.2.1` (`program.rs:2398–2490`, `bpf_loader/src/lib.rs:793–935`):

* **Уменьшить ёмкость ProgramData нельзя.** В загрузчике есть только рост (`ExtendProgram`); единственный способ
  «вернуть» лишнее — `Close`, после которого адрес программы использовать больше нельзя.
* `solana program extend <PROGRAM_ID> <ADDITIONAL_BYTES>` платит **плательщик**; сумма — только недостающая рента:
  `max(0, rent(новая длина) − текущие lamports ProgramData)` по **текущей** ставке.
* Расширение возможно только у **upgradeable** программы: если upgrade authority снята (`--final` /
  `set-upgrade-authority --final`), CLI отвечает «is not upgradeable», загрузчик — `Immutable`. Подпись самой upgrade
  authority CLI 4.2.1 для `extend` не требует (отправляется `ExtendProgram` без проверки authority, подписывает
  плательщик) — но держать ключ authority нужно в любом случае, он нужен для upgrade и для сохранения самой возможности.
* Пока активна фича `loader_v3_minimum_extend_program_size` (SIMD-0431), расширение — не меньше 10 KiB, если до
  потолка 10 MiB остаётся больше; «расширено в этом же слоте» повторно нельзя.
* При **upgrade** (`solana program deploy` поверх существующей программы) CLI ≥ 2.1 по умолчанию сам расширяет
  ProgramData, если новый `.so` не помещается (`auto_extend`, отключается `--no-auto-extend`; в `v1.18.26` его нет).
  Поэтому `exact` на devnet — рабочая политика: рост оплачивается в момент роста, по тогдашней ставке.

## 6. Прерванные деплои и buffer-аккаунты

Если `solana program deploy` оборвался после создания буфера, в сети остаётся buffer-аккаунт с заблокированным SOL
(при `exact` и 5 080 lamports/байт — около 12.7 SOL для `aof_core`). Повторный запуск `deploy-devnet.sh` безопасен
(развёрнутые программы пропускаются), но создаст **новый** буфер, а старый останется.

Скрипт **ничего не закрывает автоматически**. Шаг 5 показывает найденные buffer-аккаунты оператора (тот же фильтр,
что у `solana program show --buffers`: тип 1, `Some(authority)`) и сколько в них заперто; эти lamports **не**
засчитываются в доступный баланс. Решение — за владельцем:

* продолжить деплой — нужен keypair буфера (seed phrase CLI печатает при сбое): `solana program deploy --buffer <keypair> …`;
* вернуть SOL, если деплой не нужен: `solana program close <BUFFER> --url <RPC> --keypair <ключ оператора>`
  (вручную, после проверки адреса и authority).

## 7. Что проверено, а что — нет

Проверено в песочнице (офлайн, поддельный JSON-RPC-узел `scripts/devnet_mock_rpc.py` разбирает настоящие
сообщения `getFeeForMessage`): арифметика модели на независимых формулах, отказ по каждой политике и каждому виду
сбоя RPC, агрегатный баланс (граница в 1 lamport), порядок событий, идемпотентность и возобновление `deploy-devnet.sh`,
проверка после деплоя, отказ при чужом кластере, отсутствие путей «закрыть/создать ключ/менять authority» в скрипте.

**Не проверено в песочнице** (нет `solana`, `anchor`, `cargo`, сети до RPC) и остаётся на машине владельца:

* живая таблица `compare`/`plan` на devnet-RPC (реальная ставка за байт на момент деплоя);
* реальные размеры `.so`, их SHA-256, соответствие keypair адресам (`rotate-program-ids.mjs --check` проверяет
  только текст репозитория и печатает `[ключа нет]`);
* эксперимент «жизненный цикл buffer» на local validator: payer до/после `write-buffer`, после `deploy`, минимум баланса в ходе
  деплоя (`getTransaction` → `preBalances/postBalances` плательщика), закрытие буфера, поведение `extend` и отказ у
  программы без authority. Модель выше выведена из исходников `v4.2.1`; эксперимент — независимая проверка. Запускать
  его **только** на локальном валидаторе (`solana-test-validator` во временном ledger), не на публичной сети;
* `solana program deploy` на живой сети: по условиям задачи в песочнице не выполнялся и не будет без отдельного разрешения владельца.
